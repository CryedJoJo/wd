# part 4 文件管理系统（网盘项目）

## 面试开场 · 项目介绍

这个项目是用 C 语言基于Linux平台的一个 私有协议远程文件系统，客户端使用命令行操作，服务端用 epoll + 线程池支撑并发。客户端命令行操作，支持多用户注册登录、目录管理、文件上传下载。其实项目主要就是围绕 文件如何管理 以及 文件如何传输 进行开发的。

文件管理方面最开始用的是linux系统作为真实的文件管理系统，后来改用mysql数据库模拟文件森林。我用 MySQL建立了一张user 表和 一张file 表支撑整个逻辑。user 表存账号、随机盐值和密码散列，注册登录完全走应用层用户体系，不依赖 Linux 系统账号；file 表通过 father_id 建立父子目录关系、belong_user 区分用户，这样数据库里每条记录就是树上的一个节点，每个用户一棵树，合起来就是一片文件森林。用户看到的是虚拟路径，真实文件统一改名为内容 hash 存到服务器固定的 storage 目录——虚拟路径、文件记录、物理文件三者由数据库维护映射。

文件传输方面支持断点续传、极速秒传以及零拷贝，这些功能的实现是靠数据库模拟的文件森林支持的。并且使用了短命令分离机制，客户端命令行支持ls、cd、mkdir、pwd等短命令，以及puts、gets这种上传下载的长命令，短命令主线程当场处理，长命令投递到任务队列，由线程池的工作线程处理，主线程不会被文件传输阻塞。新连接的身份验证靠 JWT：登录成功后服务端用 HS256 签名签发 token，客户端每次请求都携带，服务端每条命令都验签、查过期。

整个项目的技术逻辑串起来就是：文件森林 → hash 存储 → 秒传/去重 → 断点续传 → mmap 高效传输 → epoll + 线程池支撑并发 → JWT 保证身份

3. 别把" mmap = 零拷贝 "说死——准确说法是"mmap 减少用户态缓冲区的拷贝，严格零拷贝是 sendfile"，这个区分见 4.6 回答。

## 4.1 问：多用户登录/注册怎么实现的？

服务端用数据库的 user 表维护用户信息，user表中将用户id作为主键，表中有用户名、密码盐值、密码散列。注册流程是：先查重用户名，然后（从 /dev/urandom） 取随机数生成一个随机盐值（格式是 `$6$随机串$`，$6$ 表示用 SHA-512），用 crypt 函数对"盐值+密码"做散列，把盐值和散列值一起存进 user 表，同时给这个新用户在文件森林表里插一条 father_id=-1 的根目录记录，他的虚拟文件系统就从这棵树的根开始长。

加盐是为了防彩虹表反查以及实现同密码不同散列。另外我们做的是应用层用户体系，不依赖 Linux 系统账号，用户注册、登录都完全由数据库驱动。

登录验证时，服务端按用户名查出 这个用户自己的盐值 ，用同一个算法对客户端输入的密码重新散列，和库里存的密码散列 做字符串比较，一致才通过。因为盐值每个用户随机生成，所以两个用户即使密码相同，库里存的两个散列值也完全不同。

登录成功之后为了让后续每个请求知道"这个请求是谁"：我不在服务端存 session，而是用账号密码验证通过后签发一个 JWT token（这个机制放在长短命令分离里展开），之后每条命令都带 token，服务端从 token 里解析出用户 id。数据隔离上，文件森林表里每条记录都带 belong_user 字段，ls、cd、mkdir、rm、上传下载的所有 SQL 都会用当前用户 id 做过滤条件，所以不同用户的数据天然隔离，用户 A 永远查不到用户 B 的记录。

## 4.2 问：数据库模拟文件森林怎么实现的？

 早期版本服务器是在磁盘上给每个用户维护真实目录树，用户一多目录一深，真实文件管理非常复杂，所以后来把目录结构整个搬进了数据库。file 表一个表同时存目录和文件，关键字段有：行 id、所属用户 belong_user、父目录 id（father_id）、文件名、客户端视角的完整路径 file_route、文件类型（1 目录 2 文件）、hash 值、是否上传完成 file_complete、删除标记。其中 father_id 是核心：每条记录通过 father_id 指向自己的父目录，行 id 又被自己的子记录引用，这样表里的记录就组成一棵树；每个用户有一棵 father_id=-1 的根目录树，所有用户合起来就是一片"文件森林"。

 路径是怎么解析的：客户端看到的是 /code 这种虚拟路径，服务端收到 cd 或 ls 后做路径解析——从该用户的根记录出发，把路径按 "/" 切开，逐级用"belong_user + father_id + file_name"查下一级目录是否存在，找到就把当前目录 id 推进到新目录行；".." 通过 join 父行回退，"." 跳过，任何一级查不到就说明路径不存在。所以服务端内部操作的其实是目录行 id，完全不依赖真实文件系统。

 虚拟路径和物理存储是分离的：客户端视角的路径只是 file_route 字段维护的字符串，真实文件并不按这个路径存放——所有用户上传的文件统一改名成自己的 hash 值，存到服务器固定的 storage 目录。下载时走"虚拟路径 → 查表拿 hash → 去 storage 取文件"。

 这个设计带来两个好处：不同用户相同文件内容的hash值相同，数据库里各用户有自己的记录行指向同一个 hash 的物理文件，这是后面极速秒传的基础；二是配合 file_complete 能标记文件是否完整，未传完的文件既不能被下载也不能被秒传引用。删除文件时还要检查这个 hash 有没有其他记录引用，一条都没有才把 storage 里的物理文件删掉，避免误删别人的文件。

## 4.3 问：断点续传怎么实现的？

 核心思想就是记录"已经传了多少"，下次从这个偏移继续，而不是重头传。以下载为例：客户端发起 gets 之前先 stat 本地同名文件，把本地已有大小当作偏移发给服务端；服务端根据用户和文件名查到该文件的 hash，再 stat storage 里的物理文件得到完整大小——本地小于服务端就走续传，把 offset 返回给客户端；客户端开传输线程从 offset 处接收数据、lseek 到 offset 处继续写本地文件，服务端从 offset 处开始发。

 上传方向反过来：上传中断后，数据库里留着一条 file_complete=0 的记录，storage 里的物理文件也只有前半部分，这个已存部分的大小就是断点。下次上传时服务端把 offset 告诉客户端，客户端从 offset 处继续读文件发送，服务端 lseek 到 offset 接着写。这里有个必须处理的设计问题：未完成的文件绝不能当正常文件用，所以我用 file_complete 标记——为 0 时它不能被别人下载、也不能参与秒传；只有收齐全部字节、校验实际大小和声明大小一致后，才把记录改成已完成。另外只有"同名且同 hash"才续传，同名但 hash 不同说明是另一个文件，服务端会清掉旧记录旧数据重新传。

 续传和大文件传输是天然配合的：发送端 mmap 整个文件之后，直接从 map+offset 的位置 send，天然支持断点续传（sendfile 的 offset 参数同理）。传输中断的检测也简单：接收方 recv 返回 0 说明对端关闭，此时如果还没收齐就保留未完成状态，下次接着传。

## 4.4 问：极速秒传怎么实现的？

 秒传是建立在"文件按 hash 命名存储 + 数据库维护文件森林"这个设计上的。客户端上传前先对本地文件算hash值，把 hash值连同文件名、大小、目标路径发给服务端。

 服务端收到后分情况判断：第一，当前用户当前目录已经有同名同 hash 的完整文件，直接回"秒传成功"；第二，全库（任何用户）已经有该 hash 的完整记录、且 storage 里物理文件真实存在——说明服务器已经有这份内容了，就不再接收文件数据，只给当前用户插一条指向该 hash 的文件记录，返回"极速秒传成功"；第三，hash 不存在或只有未完成记录，走正常上传——先插一条 file_complete=0 的记录，如果存在同 hash 的未完成记录则走断点续传。

 所以秒传的本质不是"把文件瞬间传过去了"，而是"服务器发现自己已经有这份文件，省略了内容传输，只增加一条数据库映射记录"，真正上传的数据只有一个几十字节的 hash。因为是用于内部存储文件，所以我们认为冲突不存在，理论上如果有hash冲突的话可能需要做二次hash来避免冲突。

## 4.5 问：长短命令分离怎么实现的？

 服务端主线程用 epoll 同时监听 listen fd 和所有客户端连接，具备识别长短命令的能力。连接是非阻塞的，主线程给每个连接维护读缓冲，攒齐一个完整请求 struct 后看 cmd 字段：ls、cd、pwd、mkdir、rm 这类短命令，主线程当场就处理（查库、回包，都是毫秒级）；gets、puts 这种要持续传输文件的长命令，主线程把任务投递到任务队列，由线程池的工作线程处理，主线程立刻回到 epoll 继续服务其他连接。这样就避免了"一个连接长期占着一个子线程空等命令、后来的连接饥饿"的问题。

 客户端也做了同样的分离：短命令由主线程发；执行 puts 或 gets 时，客户端主线程只发一个"准备请求"（带 hash、大小、路径），收到服务端确认后创建一个子线程，子线程新建一个 socket 专门用于文件传输，主线程继续等用户输入——传文件期间用户还能照常 ls、cd。

 但新开的 socket 是一个全新的 TCP 连接，服务端需要知道它属于哪个用户、要操作哪个路径，所以引入了 token 机制。客户端首次连接通过账号密码验证之后，服务端用 JWT（HS256，基于 HMAC-SHA256）对用户信息 签名 生成 token 字符串——payload 里放用户 id、用户名、签发时间、过期时间——发回客户端；客户端存起来之后,每条命令的请求 struct 都带上这个 token，服务端收到客户端的请求后，先验签、再查过期时间，合法才执行。客户端子线程新建 socket 连接时，同样把 token 和执行命令的路径放在传输请求里发过去，服务端验证 token 合法性、解析出用户 id，再结合路径确定操作对象，验证通过后才由工作线程进行文件的上传下载。

 两个实现细节：传输连接交给工作线程时，主线程会把它从 epoll 里摘掉并恢复阻塞模式，之后文件数据流完全由工作线程独享，主线程不会误读文件数据；准备连接则留在 epoll 里，工作线程只回确认包。另外请求 struct 里带着客户端自己维护的当前路径，服务端不保存每个连接的会话状态、完全无状态——这正是用 token 而不是 session 的原因。

## 4.6 问：mmap 零拷贝怎么实现的？

 传统文件发送是 read+send 组合：数据从磁盘到内核页缓存，再拷进用户态缓冲区，再从用户态拷进 socket 发送缓冲区，一共要经过用户态、发生 4 次上下文切换，大文件场景开销很明显。

 项目里文件大于 100MB 时，发送端用 mmap 把整个文件映射到进程虚拟地址空间，映射之后用户态直接通过指针访问页缓存，发送时直接 send(map+offset, n)，数据从页缓存直达 socket 缓冲区，省掉了 read 那次用户态缓冲区的拷贝，这就是项目里的"相对零拷贝"。配合断点续传，从 map+offset 的位置开始发即可。接收端按设计只做普通 write——因为接收端用 mmap 要边收数据边填映射区、最后还得二次 ftruncate 处理多余字节，实现复杂收益又不高。

 面试时要说得准确一点：mmap 严格意义上不算真正的零拷贝，它只是减少了用户态缓冲区的参与；内核真正意义上的零拷贝是 sendfile——文件到 socket 的传输完全在内核态完成，不经过用户态，而且 sendfile 同样支持 offset，也天然支持断点续传。那为什么项目选 mmap：因为 mmap 映射之后数据在用户态可见，方便做 hash 计算、分片等用户态处理，灵活性更高；如果纯粹是"磁盘文件直接扔给 socket"的场景，sendfile 才是最优选择。这个区分也是面试官常挖的点。

补充一点：你原回答里"jwt 加密生成 token"建议改成" jwt 签名生成 token "——JWT 的签名解决的是完整性和身份认证，不是保密，面试时这个词说错了会被追问。
